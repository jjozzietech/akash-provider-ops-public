## // what shipped

**The internet connection was replaced. The provider now runs on 2000/500.**

The old service was the binding constraint on the re-audit. Provider-side
measurement after the cutover: median **2069 Mbps down / 535 Mbps up** at 2–3 ms
with no loss, across 9 runs against 3 Sydney ISPs. The audit harness
independently measured **2074.47 down / 535.93 up**, 1.76 ms latency, 0.08 ms
jitter over 8 runs.

Two independent measurements landing within noise of each other is worth more
than either alone, and the harness figure can be verified by anyone from the
live endpoint rather than taken on trust.

Worth recording what the on-chain attributes said before: **800 / 85**. They had
been materially understating the connection, and were rounded down from the
measured medians rather than up.

One measurement note. The firewall's own CLI reported 474 Mbps upload — below
the threshold the re-audit needed — and that figure turned out to be a
limitation of the tool, not the link. Provider-side measurement returned 535. A
number from the most convenient source nearly closed off a path that was
actually open.

**A second GPU model went live.**

An RTX 3060 12 GB replaced a display card in a node that had never carried a
rentable GPU. The provider now advertises two models — RTX 3090 24Gi and
RTX 3060 12Gi, both PCIe — and the on-chain attribute set was rebuilt to the
current audit list in the process, from 28 of 29 required keys to **39
attributes**.

The second card existed for a specific reason. The RTX 3090 is under a paying
tenant lease that keeps being extended, and the audit harness needs one free
NVIDIA GPU. Evicting a paying tenant to run an audit was not an option. Fitting
a spare card was.

**The re-audit was submitted.**

`akash-network/community#1550`, filed 22 October once the harness run came back
clean: 5 of 5 functional checks passing, 7 of 7 benchmark groups complete, zero
failures.

The attestation was removed on 18 August in an auditor scope change. What that
has cost is in the next section.

**Certificates renewed**, both valid to January. What the renewal turned up is
also in the next section.

**The community blacklist took its first outside contribution.**

Another operator — RHITE, running `provider.akash.rhite.co.uk` — filed a report
through the repo's own issue template, unprompted. It landed as the list's first `cpu-miner` entry — a category that
had existed unused since the repo was created. The list stands at **40 entries**.

Their submission was better evidenced than any of the 39 that preceded it. All
39 are auto-detections from this provider's own scripts, with no reference a
third party can check. This one carried the tenant's container command array
lifted from the reporting operator's own cluster, with the deployment sequence,
which resolves on-chain for anyone who wants to verify it independently.

Accepting it exposed three gaps in the repo's own documentation, all since
fixed: the categories were named but never defined; the contribution guide
listed no evidence form covering a declared-but-unexecuted workload, which is
exactly what the submission rested on; and the issue template's confirmation
checkbox assumed observed execution, so the reporter had to rewrite it in order
to file honestly.

That last one is worth dwelling on. A contributor should not have to edit your
form in order to avoid overclaiming.

## // what broke

**Every tenant host was being served a self-signed certificate.**

Found during the October certificate renewal. Not by an alert.

The gateway carries two HTTPS listeners on 443: one for `*.ingress`, holding the
Let's Encrypt wildcard, and one with no hostname at all, holding a secret the
documentation describes as "a self-signed placeholder … until you replace it."
It had never been replaced. Tenant routes carry no section selector, so each
attached to **both** listeners — and nginx prefers an exact-hostname server
block over a wildcard one. Every tenant host therefore resolved to the
placeholder: a self-signed certificate, valid to 2036, issued to the provider's
own name.

The gateway had been reporting `OverlappingTLSConfig=True` throughout. Nothing
read it.

Nothing failed. No request errored, no pod restarted, no log line was written.
The configuration was internally consistent and quietly wrong, and it took a
routine task that happened to touch the same objects to surface it. Best
estimate is that it dated from the Gateway API migration.

Fixed: the placeholder secret now carries the real wildcard, and the renewal
script writes both secrets on every run so it cannot drift again. Filed
upstream as `akash-network/support#670`, because the default installation
produces this on any provider that leaves the placeholder in place — and the
documentation does not say that the placeholder is served to *all* tenant
hostnames rather than only custom domains.

**Active tenant leases fell from 43 to 29, and the cause is upstream of this
provider.**

Report #2 documented why. Orders carrying a `requirements.signed_by.any_of`
constraint naming an auditor are unmatchable at the chain level without that
attestation — the bid engine declines, correctly, every time and silently,
because a declined bid writes nothing anywhere. Console's default deployment
flow filters to audited providers, so the affected population is not small.

The mechanism is attrition without replacement rather than tenants leaving.
Existing leases run to their natural end and almost nothing arrives to replace
them. **One lease was created this month and it was this operator's own audit
deployment.** Genuine new tenant leases: none.

This is the single largest determinant of this provider's market access, and as
of this report it has a submission rather than a resolution.

**Thirty-one workloads were still running for leases that had already closed.**

Found on 14 October. Twenty-one closed normally, ten for insufficient funds; the
provider never reconciled the workloads away. Alongside them, the migration
spare node had been powered off and NotReady since 26 September — **eighteen
days** — hidden from the daily health check by an exclusion written into the
check itself.

Removing the orphans took Ceph raw usage from 71 GiB to 41 GiB.

Root cause: lease-close events missed during outages, and no periodic
reconciliation to catch what the event stream drops. That is report #1's silent
partition repeating, except this time the monitoring was part of the
concealment.

**The inventory operator was blind to the new GPU.**

Draining the node for the card swap used `--force`, which deleted a
controller-less inventory discovery pod. The operator never recreated it. After
the RTX 3060 was fitted the node was labelled with storage only — the GPU was
invisible to bidding. Nothing alerted. It was found because expected labels were
missing.

An issue filed by this operator on 1 October concerns the same component failing
silently in a different way: it excludes StorageClasses without a required label
and emits nothing at any log level. Three weeks later the same operator went
quiet about a GPU.

**An unattended package upgrade silently desynced the GPU driver.**

The host was running kernel module 580.173.02 against userland 580.178.04, left
by an unattended upgrade that installed new packages without a reboot. The node
looked healthy for 39 days. The mismatch surfaced only because someone was about
to depend on that GPU.

Fixed by the reboot the upgrade never triggered, then `apt-mark hold` on the
NVIDIA packages across the GPU fleet so it cannot recur.

**Provider memory grows, and an OOM kill is the known end of it.**

Measured at roughly 240 MiB a day. Against the 4 GiB limit that is about two and
a half weeks, and per the corrections below the provider was OOM-killed once
already in September. A restart on 19 October cleared in-memory retries and
slowed the rate temporarily; it has since returned to the same slope. Three
restarts in the measurement window mean there is no clean series.

Unresolved. Stated here because a known, measured, unfixed problem is worth more
in this report than silence.

**A hazard that turned out not to be one.**

The miner-eviction script triggers a `helm upgrade` on every eviction, one of
which fired on 13 October. This was flagged internally in September as a risk to
any locally patched chart: an upgrade nobody is watching could revert a patch.

Investigated this month and the risk does not exist as described. Both eviction
scripts pass `--reuse-values` against the live chart version and re-apply the
probe patch afterwards, so attributes and patches survive. Recorded because a
flagged risk that proves unfounded deserves retracting as plainly as a real one
deserves reporting.

## // corrections

Three, all this operator's.

**1. The lease counts in reports #1 and #2 were inflated.**

Both reported "active lease namespaces" — 98 and 78 — from a script whose
namespace filter was anchored on exact names, so roughly twelve system
namespaces were counted as leases every time, plus orphaned namespaces from
closed leases that nothing had cleaned up.

Reconstructed from the chain, the real active tenant lease counts at those same
measurement dates were **75** and **43**, against **29** now. The method was
validated by reproducing the current live count exactly.

The direction of the trend was right. The numbers were not, and they were the
headline figure in both reports. Found only because this report forced three
disagreeing lease figures to reconcile.

The counting script has been fixed.

**2. "It recovered on its own once the network stabilised."**

Report #2 said that of the four-day bid outage, 18–21 September. The upgrade
record shows the provider was OOM-killed on 22 September at 22:05 — the same day
bidding resumed. The recovery may have been that restart, not network
stabilisation. The claim is not supported by the evidence as it stands, and it
should not have been stated as confidently as it was. The memory growth above is
the same failure still in progress.

**3. "Upstream main has had no commits in over two months."**

Report #2 said that of `cosmos/awesome-cosmos`, where a contribution has been
pending since July. The actual figure is **two years**. The conclusion — that the
repository is dormant rather than slow — was right; the number supporting it was
wrong by a factor of twelve, and it was published.

**`#1552` is the one that is not about this provider.** Every
`[Provider Audit]` issue in the repository is unassigned — six open, the oldest
26 days — because the workflow meant to assign them references a third-party
action that no longer exists. Fifteen consecutive failures, no successful run

rather than an outage, but it had been failing silently for over two months.

series has carried it since report #1. Upstream `main` has had no commits in

reviewer with write access, **and** a requirement for verified commit
signatures.

That second blocker had never been recorded here. It was also the only one
within this operator's control, and it has now been closed — commit signing is
configured and every commit from this workstream is signed. Worth having
regardless of a repository that will not merge anything.

The contribution stays open. Checking it does not.
